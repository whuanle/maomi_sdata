# DuckDB 内存故障复盘（2026-11-20）

> 关联：[SDD](sdd.md) · [BDD](bdd.md) · [TDD](tdd.md) · [SOP](sop.md) · 证据：`tests/SData.Store.Tests/DuckDbMemoryRootCauseTests.cs`、`AnalyticsSearchSqlTests.cs`、`RollupTests.cs`、`DuckDbResourceTests.cs`

## 已复现的结构性缺陷

1. **结果限制太晚**：驱动`UseStreamingMode`默认false，执行先物化全部结果，再由应用读取N行。独立128MB临时库中50万行、每行1024字符，仅读取一行，进程RSS约38→540MiB；关闭结果后回落。该峰值不受DuckDB追踪内存完整约束，不应误称永久泄漏。
2. **汇总写放大**：带(name,labels_hash,bucket_ts)复合ART索引的汇总表每30秒删插最近窗口。独立128MB库同3万组重复100轮，带索引文件约130MB、无索引约4MB；BASE_TABLE缓存随之增大。缓存可淘汰，但高频重写与文件膨胀会竞争资源；未证明现场FATAL仅由此产生。
3. **生命周期缺口**：旧回填DELETE与INSERT分开提交，计算失败可丢旧汇总；全局rollup表没有过期清理。日志Appender未参与统一写门，查询也无统一准入。

## 修复与防复发

- 分析结果执行层绑定外层LIMIT N+1并流式读取；保留参数、排序与截断语义。执行器默认30秒预算，覆盖准入与原生计算，周期Cancel并等待退出后释放连接。
- 查询并发默认1、线程默认2；Appender事务共用写门，实际列序缓存兼容旧表。并发控制不是独立内存配额。
- rollup按桶计算临时结果，再事务替换；查询门→写门顺序，与前台重查询和摄取避免无界并发。启动幂等移除两个汇总索引；按指标热+冷总保留期清理过期汇总。
- 启动日志记录实际有效限制及线程；Debug资源采样提供类别；分析/摄取/聚合失败时每30秒最多一次安全资源摘要，不含SQL参数或业务正文。
- 已恢复故障不展示在消费页，但服务日志不删除；隐藏提示不等于修复。

## 可复核实验

`dotnet test tests/SData.Store.Tests --filter FullyQualifiedName~DuckDbMemoryRootCauseTests --logger "console;verbosity=detailed"`

同版本引擎v1.5.6的较小自动对照：10万行结果，私有内存32.4→157.1MB，执行层限制+流式约32.6MB；5千组回填30轮，带索引3,158,016字节、无索引798,720字节。绝对内存值依宿主/分配器变化，自动测试不对RSS设易波动硬阈值。

修复回归覆盖50万行只取2行重复5轮、原生超时后再查询、同桶重复30轮及重开数据库、汇总保留边界、128MB下20轮摄取/宽查询/回填/CHECKPOINT。它们不是数天生产压力测试，仍需部署后检查搜索P95、摄取吞吐、积压及类别内存趋势。

## 仍有的限制

- LIMIT不限制GROUP BY、排序、JOIN的全部中间内存，单行大值、极高基数或无限保留仍可能超过预算；超时不能保证在内存耗尽之前发生。
- memory_limit不是进程RSS上限；缓冲按条数而非总字节计量，巨大载荷还需独立接入预算。不能保证任意SQL和任意负载永不OOM。
- 索引移除不会承诺旧文件立即缩小；不要删库/WAL来“释放内存”。数据库已FATAL失效后需要协调重启，不能靠普通重试修复引擎状态。
- 本轮未重启服务、未修改现场数据、未提高部署内存限制；现场因果闭环需要上线后观察或经授权补充只读诊断。
